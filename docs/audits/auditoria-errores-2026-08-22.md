**Arreglo:** agregar `AND COALESCE(status,'published') <> 'draft'` a las tres `close_*_for_course` (un borrador nunca fue visible: no hay nada que cerrar) y, en una migración de reparación, devolver a `draft` los ítems que el backfill cerró y que no tienen ninguna entrega.

### 3. Una pregunta cerrada MÚLTIPLE con "permitir cambiar respuesta" apagada admite una sola opción
**A quién:** estudiante — no puede completar la pregunta ni retirarse de ella.

`supabase/migrations/20261680000000_poll_questions_multi_select.sql:113-124` — leí el RPC completo: el guard de `allow_change_response` está dentro de `IF v_q.type = 'cerrada'` pero **antes** del `IF v_q.multi` (`:127`), y su condición es solo "existe fila para (pregunta, usuario)", sin distinguir completar de cambiar. Peor: el caso "array vacío = borrar" (`:131-136`) está **después** del guard, así que tampoco puede destildar.

El cliente asume lo contrario de forma explícita — `src/routes/app.student.polls.tsx:1443-1450` deja `disabled={!open || isSaving}` con el comentario "marcar una segunda opción es COMPLETAR la respuesta, no cambiarla. El RPC igual valida". Y la combinación es alcanzable sin nada raro: el Switch "Permitir cambiar respuesta" se renderiza para todos los tipos incluido `mixed` (`app.teacher.polls.tsx:2517`) y el Switch `multi` de `PollQuestionsEditor.tsx:407` es independiente (solo se bloquea con `q.locked`). No hay migración posterior que lo corrija.

**Reproducción:** encuesta `mixed`, apagar "Permitir cambiar respuesta", agregar una cerrada con "Permitir varias respuestas" y 3 opciones, publicar. El alumno toca A → "Respuesta guardada". ### 4. El deploy de edge functions genera un `config.toml` que descarta 11 de los 13 `verify_jwt=false`
**A quién:** todos, en silencio — rompe el reintento de calificación IA y el drenado worker→edge.

```
ai-generate-questions, ai-grade-submission, request-password-reset,

```

Una función ausente del config se despliega con el default del CLI (`verify_jwt = true`). Y `_shared/**` fuerza `deploy_mode=all` (`:166-170`), así que las 11 se redesplegaron con el flag apagado cada vez que cambió `_shared`. El run igual termina en verde.

**Corrección al reporte original que recibí:** `verify_jwt=true` acepta cualquier JWT válido, incluida la anon key que manda `supabase.functions.invoke` — así que los caminos invocados desde el navegador (`request-password-reset`, `confirm-password-reset`, `public-attendance-check-in`, el flujo sync del docente) **no** se rompen. Lo que se rompe es todo caller que no manda un JWT parseable:

- `trigger_retry_failed_ai_gradings` (mig `20260525110000:71-89`) hace `net.http_post` con headers `{Content-Type, X-Trigger-Secret}` y **sin** `Authorization`. El gateway responde 401 antes del handler; `net.http_post` es fire-and-forget, así que no hay excepción, no hay audit log, no hay fila. El cron cada 30 min nunca reintenta una calificación con error transitorio.
- `ai-generation-worker` invoca `ai-generate-questions` / `generate-contents` con `Bearer <service_role sb_secret_*>` → `401 UNAUTHORIZED_INVALID_JWT_FORMAT`, que es literalmente el síntoma que CLAUDE.md documenta como reportado y la razón por la que esas dos declaraciones existen. El arreglo está en el repo y nunca llega al proyecto.

**Arreglo:** derivar el config mínimo de `supabase/config.toml` (parsear los bloques `[functions."x"]` y emitir su `verify_jwt`) en vez de mantener la copia a mano, y fallar el run si alguna función con `verify_jwt=false` en el repo no aparece en el config generado.

### 7. `ai-generate-sql` (y `ai-generate-report`) pueden servir el prompt de OTRA institución
**A quién:** docente que recibe SQL bajo reglas ajenas; Admin cuya personalización queda ignorada en silencio.

`supabase/functions/ai-generate-sql/index.ts:88-110` — `resolveSystemPrompt` consulta `ai_prompts` con el `admin` (service_role, bypassa RLS) filtrando solo por `use_case` y `course_id`, rankea course→3 / tenant→2 / else→1 y devuelve `sorted[0]`, **sin comparar `tenant_id` con el del caller**. El seed de `20261620000000` inserta la platform-default **más una fila por cada tenant** (bucle `FOR r IN SELECT id FROM public.tenants`), así que hay N filas empatadas en rank 2 y el sort estable de V8 se queda con la primera que devuelva PostgREST (sin `ORDER BY` → orden arbitrario).

El fix precedente existe literalmente 300 líneas más allá, en `supabase/functions/tutor-chat/index.ts:396-408`, con el comentario que describe este mismo modo de falla ("Sin esto, el prompt global de OTRO tenant (rank 2) podía servirse al tutor de este curso"). `ai-generate-report/index.ts:50-71` repite el hueco con `use_case='report_generation'`.

El escenario es alcanzable: la policy `ai_prompts_admin_write_global` (`20261360000000:26-50`) permite al Admin de tenant escribir su fila global para cualquier use_case **excepto** los `platform_support*`/`support_triage` — `sql_generation` no está excluido — y `AdminPromptsPanel.tsx:312` lo expone sin restricción a SuperAdmin. `SqlPageEditor.tsx:174` pasa `courseId: courseId ?? null`, así que una hoja SQL de pizarra sin curso cae directo en la rama `is('course_id', null)`.

### 11. El failover no rota cuando la key principal de Gemini es inválida (Gemini devuelve 400)
`supabase/functions/_shared/ai-failover.ts:17` — `ROTATABLE_STATUS` no incluye 400, con el comentario "el body es idéntico → fallaría igual". La premisa es falsa para el provider **por defecto**: la evidencia está en el mismo repo — `_shared/ai-error.ts:56-62` detecta key inválida por BODY (`API_KEY_INVALID`, `api key not valid`) además de por status, y su encabezado cita el síntoma observado ("El docente que ve *Error de IA [400]: …*").
